# v3.0.0 Step 4 (Anti-AFK) Human Behavior Analysis

## Current Implementation Analysis

### Current Behavior Patterns
1. **Movement**: Direct Baritone pathfinding to exact coordinates
2. **Timing**: Immediate movement after arrival (no pause)
3. **Path Selection**: Always optimal path (Baritone's default)
4. **Arrival Detection**: Exact 3-block threshold
5. **Queue Management**: Perpetual queue with fixed replenishment
6. **Speed**: Baritone's default movement speed (consistent)

### Potential Detection Vectors

#### 1. **Perfect Pathfinding**
- **Issue**: Baritone always takes the optimal path
- **Human Behavior**: Players often take slightly suboptimal routes, especially when:
  - Avoiding obstacles manually
  - Taking shortcuts through familiar terrain
  - Making small navigation errors

#### 2. **Immediate Movement**
- **Issue**: Movement starts instantly after arrival
- **Human Behavior**: Players typically:
  - Pause 0.5-3 seconds after arriving
  - Look around (rotate camera)
  - Check inventory/chat occasionally
  - Sometimes backtrack slightly

#### 3. **Consistent Timing**
- **Issue**: Fixed intervals between movements
- **Human Behavior**: Variable timing:
  - Sometimes move immediately
  - Sometimes pause 2-5 seconds
  - Occasionally longer pauses (5-15s) for "AFK checks"
  - Rare longer pauses (30-60s) simulating breaks

#### 4. **Exact Coordinates**
- **Issue**: Always targeting exact queue coordinates
- **Human Behavior**: Players:
  - Don't always go to exact spots
  - Sometimes stop slightly before/after target
  - Visit nearby areas multiple times
  - Have "favorite spots" they return to

#### 5. **No Backtracking**
- **Issue**: Always forward movement
- **Human Behavior**: Players sometimes:
  - Realize they went the wrong way
  - Return to previous location
  - Explore areas they just left

#### 6. **Perfect Arrival Detection**
- **Issue**: Always stops at exactly 3 blocks
- **Human Behavior**: Players:
  - Sometimes overshoot slightly
  - Sometimes stop short
  - Don't always reach exact destination

#### 7. **No Idle Behavior**
- **Issue**: Constant movement
- **Human Behavior**: Players:
  - Occasionally stop to "check something"
  - Pause to read chat
  - Stop to look at surroundings
  - Sometimes just stand still for 10-30 seconds

## Recommended Improvements

### Priority 1: High Impact, Low Risk

#### 1.1 Variable Arrival Pause
**Implementation**: Add random delay (0.5-3s) after arrival before next movement
```java
// After arrival callback
int pauseMs = 500 + random.nextInt(2500); // 0.5-3s
scheduler.schedule(() -> navigateToNextLocation(), pauseMs, TimeUnit.MILLISECONDS);
```
**Impact**: Makes timing less predictable
**Risk**: Low - doesn't affect core functionality

#### 1.2 Variable Arrival Threshold
**Implementation**: Use 2-4 block threshold instead of fixed 3
```java
int arrivalThreshold = 2 + random.nextInt(3); // 2-4 blocks
```
**Impact**: Less perfect arrival detection
**Risk**: Low - still within reasonable range

#### 1.3 Occasional Longer Pauses
**Implementation**: 5% chance of 5-15s pause, 1% chance of 30-60s pause
```java
if (random.nextDouble() < 0.05) {
    // 5% chance: pause 5-15s
    pauseMs = 5000 + random.nextInt(10000);
} else if (random.nextDouble() < 0.01) {
    // 1% chance: pause 30-60s (simulate break)
    pauseMs = 30000 + random.nextInt(30000);
}
```
**Impact**: Simulates human breaks/checks
**Risk**: Medium - might look suspicious if too frequent

### Priority 2: Medium Impact, Medium Risk

#### 2.1 Slight Coordinate Variation
**Implementation**: Add small random offset (±2-5 blocks) to target coordinates
```java
int[] destination = locationQueue.getCurrentDestination();
int offsetX = -5 + random.nextInt(11); // -5 to +5
int offsetZ = -5 + random.nextInt(11);
int targetX = destination[0] + offsetX;
int targetZ = destination[1] + offsetZ;
```
**Impact**: Less perfect coordinate targeting
**Risk**: Medium - might go outside region bounds (need validation)

#### 2.2 Occasional Backtracking
**Implementation**: 10% chance to revisit previous location instead of next
```java
if (random.nextDouble() < 0.10 && locationQueue.hasPrevious()) {
    // Go back to previous location
    locationQueue.goToPrevious();
}
```
**Impact**: More natural movement patterns
**Risk**: Medium - might cause queue management issues

#### 2.3 Variable Movement Speed
**Implementation**: Occasionally use slower Baritone settings
```java
// 20% chance to use slower pathfinding
if (random.nextDouble() < 0.20) {
    // Send Baritone setting for slower movement
    // Note: Requires Baritone API access or command
}
```
**Impact**: Less consistent speed
**Risk**: High - requires Baritone API changes

### Priority 3: Lower Priority, Higher Complexity

#### 3.1 Suboptimal Path Selection
**Implementation**: Occasionally add intermediate waypoints
```java
// 15% chance to add waypoint slightly off optimal path
if (random.nextDouble() < 0.15) {
    int waypointX = targetX + random.nextInt(10) - 5;
    int waypointZ = targetZ + random.nextInt(10) - 5;
    // Navigate to waypoint first, then destination
}
```
**Impact**: Less perfect pathfinding
**Risk**: High - complex to implement, might cause issues

#### 3.2 Camera Rotation Simulation
**Implementation**: Randomly rotate camera while moving/stopped
```java
// Simulate looking around
float yaw = player.getYaw() + (random.nextFloat() - 0.5f) * 60f;
float pitch = Math.max(-90, Math.min(90, player.getPitch() + (random.nextFloat() - 0.5f) * 30f));
// Note: Requires camera control API
```
**Impact**: More human-like behavior
**Risk**: High - requires camera control, might be detectable

#### 3.3 Inventory/Interaction Simulation
**Implementation**: Occasionally open inventory or interact
```java
// 2% chance every 30 seconds
if (random.nextDouble() < 0.02) {
    // Open inventory briefly
    // Note: Requires interaction API
}
```
**Impact**: Simulates player checking items
**Risk**: Very High - easily detectable, might cause issues

## Recommended Implementation Plan

### Phase 1: Quick Wins (Low Risk)
1. ✅ Variable arrival pause (0.5-3s)
2. ✅ Variable arrival threshold (2-4 blocks)
3. ✅ Occasional longer pauses (5% chance, 5-15s)

### Phase 2: Coordinate Variations (Medium Risk)
1. ✅ Slight coordinate offset (±2-5 blocks) with bounds checking
2. ✅ Occasional backtracking (10% chance)

### Phase 3: Advanced (Higher Risk - Evaluate Carefully)
1. ⚠️ Variable movement speed (requires Baritone API)
2. ⚠️ Suboptimal path selection (complex)
3. ❌ Camera rotation (highly detectable)
4. ❌ Inventory simulation (very risky)

## Testing Strategy

1. **Short-term testing**: Run for 1-2 hours, monitor for:
   - Unusual behavior patterns
   - Performance impact
   - False positives in safety checks

2. **Long-term testing**: Run for 24+ hours, monitor for:
   - Detection by server admins
   - Stability over time
   - Memory/performance degradation

3. **A/B Testing**: Compare detection rates between:
   - Current implementation (perfect timing)
   - Phase 1 improvements
   - Phase 2 improvements

| Coordinate variation | Low | Medium | Medium |

| Variable speed | Low | High | Low |

| Camera rotation | High | High | Very Low |
| Inventory simulation | Very High | High | Very Low |

## Conclusion

**Recommended Approach**: Implement Phase 1 improvements first (variable pauses and thresholds). These provide the most benefit with minimal risk. Phase 2 can be added after testing Phase 1. Phase 3 should be evaluated very carefully as the risks may outweigh the benefits.

**Key Principle**: Subtle variations are better than obvious patterns. A 5% chance of unusual behavior is more human-like than 100% perfect behavior, but 50% unusual behavior might be too obvious.
